# 보안 설계와 미검증 가정

**보안 설계 리뷰를 진행했지만 구현·침투 시험·운영 보안 검증은 수행하지 않았습니다.** 원 명세의 버전명에 검증을 뜻하는 표현이 있어도 이 저장소에서는 보안 인증이나 안전성 확보로 해석하지 않습니다.

## 검토한 위협과 대응 방향

| 위협 | 명세에서 보완한 방향 | 아직 필요한 확인 |
|---|---|---|
| 저장소 문서의 지시가 정책으로 취급됨 | 프로젝트 자료와 신뢰 정책의 경계 분리 | 실행 시 실제 로딩 경로와 권한 |
| 역할 이름만 다르고 권한은 공유 | 역할·OS 실행 주체·접근 범위 분리 | 서로의 파일·인증정보 접근 거부 시험 |
| 작업 코드의 인증정보 접근·외부 전송 | 공급자 연결과 작업 실행의 경계·통신 제한 | 설치 환경에서의 실효성 |
| 제어 계층의 정책 자기 변경 | 정책·코드 보호와 서명된 신뢰 기준 | 변조 거부·키 관리·복구 |
| 경로 링크로 보호 영역 읽기 | 번들 경계 및 링크 처리 제한 | 실제 파일시스템 경계 시험 |
| Worker가 시험을 약화해 통과 | 승인 시험과 지원 파일 보존 | 변조·누락·수집 조작 감지 |
| 새 설정 파일이 나중에 실행됨 | 실행형 설정·보호 경로 변경 심사 | 리뷰·IDE·CI 경로에서의 차단 |
| 마스터 메시지가 승인으로 오인됨 | 구조화된 별도 사람 승인 경로 | 승인 대상·내용·권한 결합 |
| 원문 로그에 비밀·개인정보 잔류 | 최소 수집·가림·접근 및 보존 정책 | 탐지·삭제·보관 검증 |

## 신뢰 경계에 대한 설계 판단

마스터와 작업 에이전트의 판단은 요청 또는 주장으로 취급하고, 상태 변경은 제어 계층이 확인하도록 계획했습니다. 제어 계층도 복잡한 외부 자료를 직접 처리하다 침해될 수 있다는 가능성을 검토해, 산출물 파싱을 분리하는 방향을 명세에 추가했습니다.

다만 제어 계층 자체가 침해되면 근거 생성·판정도 신뢰할 수 없을 수 있습니다. 해시, 서명, 별도 실행 같은 용어를 사용하는 것만으로 문제가 해결되지는 않습니다.

## 원 명세의 중요한 제한

- 문서 수준의 대응과 실제 OS·프로세스 경계는 동일하지 않습니다.
- 탐지 도구가 경고하지 않았다는 사실만으로 위험이 없다고 판단하지 않도록 설계했습니다.
- CLI·컨테이너·네트워크의 구체적 동작을 가정한 부분은 PoC 대상으로 남았습니다.
- 보안 수용 조건을 문서에 적었지만 실제 PASS 결과는 없습니다.
- 도구의 최신 정책·지원 범위·보안 상태는 이 문서에서 인증하지 않습니다.

따라서 현 단계는 **위험을 식별하고 검증 질문을 만든 설계 학습**입니다. 안전한 자율 개발 시스템을 구축했다는 실적이 아닙니다.
