# 제안 아키텍처

**명세의 목표 구조이며 모든 실행 계층은 미구현입니다.**

![설계 계층](../diagrams/architecture.svg)

## 책임 분리

| 구성 | 맡기려는 책임 | 부여하지 않으려는 권한 |
|---|---|---|
| Master | 요구 해석, 분해, 진행 설명, 복구 방향 조율 | 검수 반려 무시, 보안 승인 대행, 임의 명령 실행 |
| Custom Harness | 정책, 역할 권한, 계약, 실행 근거, 공급자 연결 관리 | 작업 저장소의 지시를 제어 정책으로 자동 신뢰 |
| Workflow runtime | 단계·조건·재시도·중단 및 재개 상태 | 자연어 완료 보고만으로 상태 승인 |
| Worker | 승인된 범위의 구현과 완료 근거 제출 | 요구사항·필수 시험을 임의 변경 |
| Reviewer | 별도 맥락에서 요구사항·변경·근거 검토 | 코드 수정·프로젝트 코드 실행 |
| Independent QA | 별도 세션과 환경에서 실제 동작 확인 | 테스트 대상이나 승인 기준을 임의 수정 |
| Wiki 역할 | 검수된 변경을 프로젝트 지식에 반영 | 검토 전 초안을 공식 지식으로 승격 |

독립성은 모델 이름을 다르게 하는 것만으로 확보되지 않는다는 설계입니다. 세션, 제공 맥락, 허용 작업, 판정 기준을 분리하려 했습니다. 실제 독립성은 아직 시험하지 않았습니다.

## 검토한 기술 후보

| 계층 | 명세에 등장한 후보 | 현재 의미 |
|---|---|---|
| Master | Hermes Agent | 대화·조율 역할 후보, 미연동 |
| 제어 계층 | Python 기반 Custom Harness | 직접 구현을 계획한 부분, 코드 없음 |
| 상태 전환 | LangGraph | 실행 상태 관리 후보, 미구현 |
| 작업 / 검수 | Codex CLI / Claude Code CLI | 역할별 연결 계획, adapter 없음 |
| QA | 독립 실행 환경, Playwright 등 | 검증 방식 후보, 시험 없음 |
| 상태·기록 | SQLite, JSONL, Git, Markdown | 저장 구조 계획, 실행 DB·감사 로그 없음 |
| Wiki UI | Obsidian | 승인 문서 탐색 방식 후보 |
| 선택적 확장 | LangSmith, PostgreSQL, Temporal | 관측·운영 고도화 검토, 도입 실적 아님 |

이는 개인의 구상에 사용된 기술 목록이지 숙련도·구현 경험 목록이 아닙니다. 각 도구가 요구하는 보안 경계나 연결 방식은 실제 설치 버전에서 확인해야 합니다.

## 상태와 지식의 구분

실행 상태와 승인 근거는 제어 계층의 기록으로 관리하고, 사람이 읽는 체크리스트는 그 상태를 표현하는 화면으로 두려 했습니다. Wiki는 승인된 지식을 탐색하는 용도이며, 작성된 Markdown 자체가 권한이나 완료 상태를 바꾸어서는 안 된다는 설계입니다.

외부 관측 서비스는 선택 사항입니다. 외부 서비스를 사용하지 못하더라도 로컬 상태와 기록으로 복구할 수 있어야 한다는 목표는 있으나 복구 시험은 하지 않았습니다.
